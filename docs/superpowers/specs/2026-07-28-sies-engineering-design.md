# SIES 默认智能体研发体系设计

**日期：** 2026-07-28

**状态：** 已批准

**名称：** Self-Improving Engineering System（SIES）

## 摘要

SIES 将成为 Devkit 的默认研发序列。它以目标一致性和不确定性收敛为进度标准，以
GitHub Issue、评论、PR 和 ADR 作为配置、证据与组织记忆层。

SIES 不取消测试。测试用于验证目标、契约和关键风险，但不再作为所有任务的默认控制
循环。TDD 被重新定位为工程化阶段内的一种可选策略。

## 问题

传统 AI Coding 工作流通常把 TDD 扩展成所有研发任务的顶层框架：

1. 需求和架构尚未稳定时，测试会过早固化未经验证的假设。
2. 同一智能体同时生成实现与测试，可能让同一种错误理解相互验证。
3. “测试变绿”只能证明实现符合测试，不能证明实现符合用户目标。
4. 每个小改动都执行 RED、GREEN、REFACTOR，会放大运行时间、上下文和 Token 成本。
5. 低价值、重复和实现细节导向的测试不断进入回归集，长期拖慢维护。
6. 测试失败容易把智能体困在局部修补循环，而不是重新审视目标或方案。
7. 固定的 GitHub 模板和阶段门禁把流程动作误当成工程质量。

SIES 需要把研发控制中心从“测试循环”转移到“目标—假设—证据—决策”循环。

## 目标

- 所有研发任务默认使用同一套 SIES 思维序列。
- 根据 L0–L3 的复杂度压缩、合并或展开阶段，而不是切换到完全不同的流程。
- 在编码前明确目标、成功信号、非目标和关键不确定性。
- 先用最低成本的有效证据验证方向，再投入生产级工程化。
- 让测试直接追溯到目标、稳定契约或真实风险。
- 在完整逻辑增量完成后统一执行目标测试和交付回归。
- 让 GitHub skills 根据现有证据自适应推进，而不是复刻固定流水线。
- 把真实经验沉淀为下一轮研发的配置输入。

## 非目标

- 不废除自动化测试或 TDD。
- 不为每个小任务创建 Issue、ADR、实验报告或复盘文档。
- 不要求每个阶段都生成独立文件、分支或 GitHub Issue。
- 不以测试数量、覆盖率、评论数量或流程步骤数量衡量质量。
- 不修改第三方缓存中的 superpowers skills。
- 不在本次改造中实现新的 GitHub App、CI 服务或运行时状态机。

## 核心原则

1. **目标优先于实现。** 先判断要达到什么结果，再判断写什么代码。
2. **证据优先于仪式。** 每个动作都应降低不确定性、验证目标或控制真实风险。
3. **Evaluation 不等于 Regression。** 前者决定方向是否值得继续，后者保护已经确认的价值。
4. **测试是证据，不是唯一证据。** 原型、基准、静态分析、用户场景、视觉检查和运行数据都可以验证目标。
5. **测试质量优先于数量。** 持久测试必须保护稳定契约或真实失败模式。
6. **原型可以丢弃。** Prototype 的职责是回答问题，不是提前完成生产系统。
7. **允许回退和停止。** Evaluation 失败时可以重新探索、调整原型或停止投入。
8. **学习必须来自证据。** 只有重复问题、高影响故障或明确可复用经验才升级为系统规则。

## SIES 生命周期

```text
Goal Contract
  ↓
Architecture Exploration
  ↓
Prototype
  ↓
Evaluation
  ↓
Refinement / Decision
  ├─ 回到探索
  ├─ 调整原型
  ├─ 停止
  └─ 进入工程化
        ↓
Engineering
        ↓
Regression Test
        ↓
System Learning
        ↺
```

### 1. Goal Contract

回答以下问题：

- 期望结果是什么？
- 谁会感受到结果？
- 哪些信号可以判断目标已达到？
- 哪些内容明确不在本次范围？
- 有哪些约束、风险和不可逆操作？
- 当前最重要的未知项是什么？

**出口条件：** 目标可以被评价，且关键未知项已经显式化。

### 2. Architecture Exploration

围绕关键未知项寻找候选路径。候选数量由不确定性决定，不强制凑够固定数量。确定性
修改可以只确认现有架构路径；复杂任务需要比较替代方案、代价、可逆性和验证方式。

**出口条件：** 至少有一个值得通过原型验证的候选方案。

### 3. Prototype

构建能够回答关键问题的最小实现、spike、脚本、交互稿、基准或集成探针。原型可以
复用，但默认不承诺生产质量，也不要求完整测试体系。

**出口条件：** 原型能够产生 Evaluation Contract 所要求的证据。

### 4. Evaluation

按照预先声明的成功信号评价原型。评价证据可以是自动化测试，也可以是用户场景、
性能数据、视觉结果、静态检查、运行日志或人工评审。

**出口条件：** 证据足以支持继续、调整、回退或停止中的一个决定。

### 5. Refinement / Decision

根据证据选择方案，并记录：

- 采用、组合、修改或拒绝了什么；
- 证据如何支持决定；
- 哪些风险仍然存在；
- 是否需要调整 Goal Contract。

**出口条件：** 已选择工程化方向，或明确停止。

### 6. Engineering

把选定方案转成可维护、可观测、兼容且可交付的生产实现。此阶段决定哪些临时证据应
转化为长期测试，并完成必要的文档、迁移、错误处理和发布约束。

**出口条件：** 完整逻辑增量实现完毕，且目标与风险已有对应验证方式。

### 7. Regression Test

在完整功能或修复批次完成后运行目标测试；交付前统一运行一次与风险匹配的项目回归。
如果回归暴露问题并导致相关代码、配置或环境变化，修复后重新运行受影响验证。

**出口条件：** 没有阻断交付的回归，或已明确记录无法验证的范围和原因。

### 8. System Learning

检查本次工作是否产生值得复用的经验。只有符合以下任一条件才形成 Learning
Candidate：

- 相同问题已经重复出现；
- 一次高影响故障暴露了系统性缺口；
- 一个新方法显著降低了成本或风险；
- 用户明确要求沉淀。

Learning Candidate 默认先进入 Issue 或学习记录。只有获得授权后，才升级为 skill、
项目约束、自动检查或模板，避免自动膨胀规则。

## 测试在 SIES 中的定位

### 进度单位

TDD 的进度单位是一次 RED–GREEN–REFACTOR。SIES 的进度单位是一个已经被证据关闭的
关键不确定性。

测试只有在能够验证目标一致性、稳定契约或关键风险时才产生价值。测试通过但目标证据
失败，整个 Evaluation 仍然失败。

### Test Strategy Gate

进入 Engineering 前，根据问题类型选择测试策略：

| 场景 | 默认策略 |
|---|---|
| 目标或需求仍不清楚 | 不写持久测试，先补 Goal Contract 和评价标准 |
| 架构方向不确定 | 用 Prototype、benchmark 或 spike 比较方案 |
| 可复现 bug | 优先编写失败复现；TDD 通常有价值 |
| 稳定业务规则或公共契约 | 可使用 TDD、example-first 或 contract-first |
| UI、体验或生成式功能 | 以场景、视觉和评价量表为主，避免脆弱快照 |
| 安全、迁移、并发、兼容性 | 提前运行高风险针对性测试 |
| 确定性的机械修改 | 实现后做最便宜的有效检查 |
| 完整逻辑增量 | 运行目标测试，并在交付前统一回归 |

### 证据阶梯

优先选择能够可靠回答问题的最低成本证据：

1. 代码与配置检查；
2. 语法、类型和静态分析；
3. 最小运行实验；
4. 针对性单元或契约测试；
5. 集成、端到端或视觉验证；
6. 项目回归。

低层证据不足以验证目标时才升级。不能为了节省成本而使用无法回答问题的检查。

### 测试晋升

Prototype 中的脚本、探针和临时断言默认是一次性评价证据。只有满足以下条件的测试才
进入长期回归集：

- 能追溯到成功信号、稳定契约或真实失败模式；
- 被保护行为损坏时确实会失败；
- 断言清晰、稳定且有助于定位问题；
- 不重复已有测试；
- 维护成本与被保护风险相称。

不要求默认覆盖率目标。没有相关代码、配置、依赖、夹具或环境变化时，不重复运行同一
套验证。

### 降低同源偏差

测试和实现都由同一智能体生成时，不能只从实现反推测试。持久测试至少应锚定以下一种
独立来源：

- 用户场景或 Goal Contract；
- 已有公共契约；
- 真实故障或生产证据；
- 外部标准、协议或兼容性要求；
- 已批准的 Evaluation Contract。

## 复杂度缩放

所有等级都遵循 SIES 语义序列，但产物深度不同：

| 等级 | 默认深度 |
|---|---|
| L0 | 阶段内联完成；目标是用户原话，探索是定位修改点，diff/静态检查完成评价；不建 Issue |
| L1 | 简短 Goal Contract；通常验证一个候选方案；Issue 可选；完成批次后做目标验证 |
| L2 | Issue 记录目标、不确定性、评价契约与决定；必要时比较方案；目标测试后统一回归 |
| L3 | 完整探索与原型证据；重要决策写 ADR；高风险验证可前移；交付前执行完整回归 |

阶段可以合并，但不能用流程简化掩盖未关闭的关键不确定性。

## GitHub 作为配置与证据层

GitHub 不负责强制线性流程，而负责保存可恢复的研发状态：

- **Issue body：** Goal Contract、Uncertainty Map、Evaluation Contract 和当前范围；
- **Issue comment：** 探索结论、原型证据、Evaluation 结果与 Refinement 决定；
- **Child issue：** 仅用于可独立推进的实验或工程增量；
- **PR：** 工程化实现、目标映射、持久测试选择与回归证据；
- **ADR：** 只保存高影响、长期有效的架构决定；
- **Learning Candidate：** 保存可能改善未来系统的证据。

仓库支持标签时可以使用一个 `sies` 标签和一个当前阶段标签。标签是查询便利设施，不是
阶段完成的证据；没有标签时仍可通过结构化标题和评论继续工作。

### Goal Contract 最小结构

```markdown
## SIES Goal Contract
- Outcome:
- Success signals:
- Non-goals:
- Constraints:
- Key uncertainties:

## Evaluation Contract
- Decision to make:
- Evidence:
- Pass / stop conditions:
```

L0/L1 可以在对话或本地计划中使用同样结构，不要求持久化完整模板。

## Skills 架构

### `sies-engineering`

新增默认研发编排 skill。它负责：

- 建立或恢复 SIES 状态；
- 判断阶段深度；
- 选择证据与测试策略；
- 调度 GitHub、语言规范和实现类 skills；
- 防止 Evaluation、Engineering 与 Regression 混淆；
- 在结束时筛选 Learning Candidate。

它不复制各 GitHub skill 的命令和安全规则。

### `using-dev`

从“按 L0–L3 选择不同流水线”改为：

1. 检测仓库、语言、风险与不确定性；
2. 默认调用 `sies-engineering`；
3. 使用 L0–L3 决定阶段深度和持久化程度；
4. 保留用户对 Issue、分支、计划和复盘的明确选择。

### `github-product-manager`

从固定多轮问卷改为不确定性驱动的 Goal Contract：

- 已知信息不重复确认；
- 只追问会改变目标、范围或评价方式的未知项；
- 验收标准改为可评价的成功信号，不强制全部转成自动测试；
- 用户已明确授权直接创建时可以跳过重复预览；
- 产物可以是探索任务，不强制伪装成实现就绪 Issue。

### `github-create-issue`

从固定七段式模板改为自适应 Issue Profile：

- Goal / Product；
- Exploration；
- Prototype；
- Engineering / Bug；
- Learning。

每种 Profile 使用不同的质量门禁。跟踪型父 Issue 可以同时容纳探索和工程阶段；只有
真正独立可交付或可并行的工作才拆成 Child Issue。

### `github-issue-workflow`

从固定 Pull → Triage → Develop → Review → Ship 改为阶段感知控制器：

- 先读取已有 Goal Contract 和证据，识别当前阶段；
- 从已有状态恢复，不重复已经完成的澄清和验证；
- 允许 Evaluation 回到探索或原型；
- 只有开始产生代码时才需要分支；
- worktree 根据工作区污染、并行度和风险自动选择，不固定询问；
- Review 深度由风险、diff 和公共影响决定，不强制每次启动独立智能体；
- 测试由 Test Strategy Gate 决定，交付前保留一次回归门禁。

## 需要移除的僵化规则

- “每个 Issue 必须完整走同一周期”。
- “无论已有信息多少都必须逐轮提问”。
- “用户已直接授权仍必须重复预览”。
- “每次开发前都必须询问 worktree”。
- “每个改动都必须启动独立 review agent”。
- “测试通过即可进入下一阶段”。
- “所有验收标准都必须转换成自动化测试”。
- “每个函数、文件或小步骤都需要独立测试循环”。
- “为了流程完整而重复运行没有新信息的测试”。

## 异常与降级

- Goal Contract 无法评价：先补成功信号或代理指标，不进入生产工程化。
- Prototype 证据不足：调整实验或回到探索，不通过增加无关测试强行推进。
- 测试通过但目标证据失败：Evaluation 失败。
- GitHub 或 `gh` 不可用：使用本地计划、commit 和交付说明保存同等信息。
- 用户要求直接执行：压缩阶段和产物，但保留最小目标、关键风险和交付验证。
- Existing Issue 信息不足：优先补充 Issue 或评论；只有独立工作才新建 Issue。
- 回归失败：先定位真实失败模式，修改后只重跑受影响检查和最终交付回归。

## 验证策略

这是一个文档与 skill 编排批次。全部改动完成前不逐文件运行回归，也不启动多轮子智能体
压力测试。交付前统一回答以下问题：

1. 新 skill 的 frontmatter、名称和本地引用是否合法？
2. README 与 `using-devkit` 是否能够发现新 skill？
3. SIES 是否明确成为默认序列？
4. GitHub skills 是否支持阶段恢复、回退和自适应产物？
5. 测试是否被定义为目标一致性证据，而非被取消？
6. TDD 是否只在合适场景作为嵌套策略？
7. 现有安装、Shell、JSON 和元数据校验是否保持通过？

最后统一运行：

- 官方 skill 结构校验；
- `npm test`；
- `git diff --check`；
- 一次本地语义自检。

## 验收标准

- `sies-engineering` 可被各支持平台发现并独立调用。
- `using-dev` 默认把所有研发任务路由到 SIES。
- L0–L3 只改变阶段深度，不改变核心研发序列。
- 三个 GitHub skills 不再要求固定线性流程或固定模板。
- Goal Contract、Evaluation Contract 和 Learning Candidate 有清晰结构。
- Evaluation、Engineering 和 Regression 的职责不再混淆。
- 测试保留且直接追溯到目标、契约或风险。
- TDD 不再是默认顶层框架，但在适合场景中可明确选择。
- 交付验证遵守“完整批次后一次高信息量回归”的项目原则。
