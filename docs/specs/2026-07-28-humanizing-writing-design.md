# humanizing-writing Skill 设计文档

## 概述

新增一个中英双语写作编辑 skill，用于减少日常写作、技术文档和 PR 描述中的模板化 AI 痕迹，同时保留事实、作者语气与文本用途。

内容基线采用 [blader/humanizer](https://github.com/blader/humanizer/blob/main/SKILL.md)。实现会保留其事实保真、语气校准、误判防护、调用模式和二次审校思路，并针对中文写作补充本地化模式。该 skill 只判断和修正写作特征，不判断文本是否由 AI 创作。

## 目标

- 支持中文和英文文本。
- 区分日常写作、技术文档和 PR 描述，不用同一套语气覆盖所有场景。
- 保留原文中的事实、名字、数字、日期、引用、链接、代码和专有名词。
- 优先匹配用户提供的写作样本，避免把个人习惯误删成“AI 味”。
- 识别成组出现的写作模式，避免因为单个词、破折号或整齐格式过度改写。
- 支持直接粘贴、文件编辑和被其他任务调用三种模式。

## 非目标

- 不充当 AI 文本检测器，也不输出作者身份或生成概率。
- 不在没有来源时补充事实、案例、统计数字、引语或引用。
- 不默认翻译文本。
- 不改写代码块、结构化数据、frontmatter、链接目标或命令。
- 不把技术文档强行改成口语，也不向中性文本注入个人观点。
- 首版不实现关键词扫描脚本。模式判断依赖上下文，机械扫描容易制造误报。

## 触发条件

用户提出以下需求时触发：

- “去 AI 味”“去机器味”“写得像人一点”“自然一点”
- 润色、改写或审校疑似模板化的中文或英文文本
- 清理技术文档、README、设计说明中的空话和生成式套话
- 清理 PR 标题或描述中的夸张表达、变更叙事和机械结构
- humanize、naturalize、remove AI writing patterns、make this sound less AI-generated

普通的事实核查、翻译、摘要和语法修正不应仅凭任务中出现文本就自动触发。

## 核心原则

1. 保留信息，不保留原文形状。允许拆并段落、调整顺序和压缩重复，但不能丢失有效事实。
2. 不发明事实。所有新增事实性内容都必须来自原文或用户提供的上下文。
3. 作者样本优先。用户提供的既有文本可以覆盖通用标点、节奏和用词偏好。
4. 按文本用途选择“人的声音”。日常写作可以保留态度和不均匀节奏；技术文档以清楚、准确为准；PR 描述以变更事实和验证证据为准。
5. 看模式组合，不看孤立信号。单个破折号、转折词、排比或完整语法不能证明文本需要重写。
6. 具体内容优先。删去无法落到事实上的拔高、营销话术、伪分析和通用结尾。

## 场景路由

| 场景 | 默认语气 | 重点保留 | 重点处理 |
|---|---|---|---|
| 日常写作 | 自然、有个人节奏 | 立场、细节、犹豫、幽默、口头习惯 | 模板化开场、假热情、排比堆叠、伪深刻结尾 |
| 技术文档 | 中性、直接、精确 | 术语、接口名、限制、因果关系、代码和链接 | 空泛价值判断、无主语片段、变更叙事、重复标题、教程式报幕 |
| PR 描述 | 简洁、可核验 | 问题、改动、测试、风险、兼容性 | “全面提升”等宣传语、夸大影响、机械三段式、泛化总结 |
| 英文文本 | 匹配原文用途和作者习惯 | 名称、数字、引用、语域 | 参考 skill 中的内容、语言、样式、交流和填充模式 |

用户明确指定语气或提供写作样本时，用户要求覆盖场景默认值。

## 调用模式

### 直接粘贴

用户在对话中提供文本。返回：

1. 改写草稿
2. 简短审校结果，指出仍显模板化的部分以及是否出现新增事实
3. 最终改写

如果用户明确要求“只给结果”，则只返回最终改写。

### 文件模式

用户指定文件。只改动自然语言内容，保留代码块、frontmatter、数据、链接目标和其他机器可读结构。内部完成草稿和审校，文件最终只包含最终改写；对话中给出简短变更摘要。

### 嵌入模式

该 skill 被另一任务用于生成 PR 描述、提交信息或文档片段。内部完成完整审校，只向调用方返回最终文本，不附带过程说明。

## 处理流程

1. 判断语言、文本场景和调用模式。
2. 查找用户提供的写作样本；存在样本时记录句长、词汇、段落开头、标点、惯用表达和转折方式。
3. 建立事实账本，记录名字、数字、日期、引用、链接、代码标识符和原文主张。
4. 按需读取 `references/chinese-patterns.md` 或 `references/english-patterns.md`，寻找成组出现的模式。
5. 生成草稿。优先使用简单句式、具体主语和自然节奏，允许重组文本但不得改变事实。
6. 完成两项审校：
   - 哪些地方仍然明显像模板化 AI 文本？
   - 是否加入了原文和用户上下文中没有的事实？
7. 修正审校结果，核对事实账本和受保护内容后输出最终文本。

## 中文模式目录

`references/chinese-patterns.md` 按以下类别组织，每类提供问题说明、观察信号、改写方向和一组前后对照：

- 套路化开场、报幕和过渡词
- 无依据的意义拔高、时代叙事和宏大结论
- 营销腔、汇报腔和“赋能/助力/打造”等空泛动词
- 抽象名词堆叠、名词化和缺少明确主语
- “不仅……更……”“从……到……”等机械对偶与伪范围
- 强行三点式、排比和过度整齐的句式
- 用“这说明/这体现/这彰显”追加的表层分析
- “业内人士认为”等模糊归因和无来源权威
- 伪坦率、伪深刻、口号式短句和制造金句
- 标题复述、碎片化小标题、粗体标签列表和通用结尾
- 聊天助手残留、迎合语气和邀请继续交流
- 英译中腔、标点堆叠、同义词轮换和均匀句长
- 不应误判的人类写作特征

规则描述强调观察“模式组合”，不把词表作为禁用词表。

## 英文模式目录

`references/english-patterns.md` 压缩整理参考 skill 的 33 类模式，并保留来源与 MIT 许可说明。内容分为：

- 内容模式：意义拔高、媒体知名度、表层 `-ing` 分析、宣传语、模糊归因、模板化展望
- 语言模式：高频 AI 用词、回避简单系动词、否定对偶、三点式、同义词轮换、伪范围、被动与无主语片段
- 样式模式：破折号、粗体、标签式列表、标题大小写、表情、引号
- 交流模式：聊天残留、知识截止声明、无依据补全、迎合语气
- 填充模式：冗长短语、过度保留、通用积极结尾、说服式权威话术、报幕、金句和戏剧化短句
- 误判保护和应当保留的人类写作信号

英文作者样本中的明确习惯优先于通用规则，包括破折号和引号风格。

## 边界和异常处理

- 没有提供待处理文本时，要求用户补充文本或文件。
- 原文事实本身含糊时，保留含糊程度或删除无依据陈述，不自行具体化。
- 用户要求判断文本是否由 AI 生成时，说明无法仅凭文风确定作者，只能列出可编辑的写作模式。
- 引用、标题、专有名词和示例中的“高频词”不因命中词表而改写。
- 文件中自然语言与机器可读内容混合时，仅编辑可以安全识别的自然语言部分；边界不清时停止改动并说明位置。
- 用户要求与作者样本冲突时，以本次明确要求为最高优先级，其次是作者样本，最后才是 skill 默认规则。

## 验证策略

采用 skill 的 RED-GREEN-REFACTOR 验证：

### RED

让 fresh-context 测试代理在不提供新 skill 的情况下，分别运行中文日常写作、中文技术文档、PR 描述和英文文本场景，记录基线输出中的问题：

- 是否保留模板化表达
- 是否过度改写或抹平作者个性
- 是否发明事实
- 是否破坏代码、链接或专有名词
- 是否没有按场景调整语气

对关键输出契约另外执行措辞微测试。无指导对照组和加载 skill 的实验组各运行至少 5 个 fresh-context 样本，逐份阅读结果，不能只靠关键词计数判断成败。

### GREEN

让测试代理加载新 skill 后重复同类场景，验证：

- 四类场景都能正确路由
- 事实账本内容保持不变
- 受保护内容原样保留
- 中文和英文模式得到针对性处理
- 日常写作、技术文档和 PR 描述的输出语气有明确差异
- 文件和嵌入模式不泄露内部审校过程

### REFACTOR

先按基线失败分类选择修正规则：输出形状错误使用正向输出契约，遗漏必需内容使用结构化检查项，需要按条件变化的行为使用可观察条件。根据验证中出现的新误判和遗漏补充规则，再重复测试。最后运行：

```bash
python /Users/zhpeng/.codex/skills/.system/skill-creator/scripts/quick_validate.py skills/humanizing-writing
npm test
```
